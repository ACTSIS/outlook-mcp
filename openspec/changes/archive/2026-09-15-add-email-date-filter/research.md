## Q1. $filter syntax for receivedDateTime comparisons

**Verdict: confirmed. `ge`/`le`/`eq` supported; DateTimeOffset literals are NOT quoted; date-only literals are accepted for message date filters (official example); full ISO 8601 with `Z` is the canonical format.**

| Claim                                                                            | Source | Quote / evidence                                                                                                                                                           | Confidence |
| -------------------------------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| Relational operators `lt`, `gt`, `le`, `ge` are supported in Graph `$filter`     | S1     | "Relational operators: Less than (`lt`), Greater than (`gt`), Less than or equal to (`le`), Greater than or equal to (`ge`)"                                               | high       |
| DateTimeOffset values are unquoted in `$filter` expressions                      | S1     | "GUID and DateTimeOffset values aren't enclosed in quotes in `$filter` expressions."                                                                                       | high       |
| Timestamp-with-Z syntax is the documented form for datetime comparison           | S1     | `~/devices?$filter=registrationDateTime le 2021-01-02T12:00:00Z` (syntax table, `le` row)                                                                                  | high       |
| Date-only literals are accepted on message receivedDateTime, combined with `and` | S1     | "Get all emails received by the signed-in user in April 2017": `~/me/mailFolders/inbox/messages?$filter=ReceivedDateTime ge 2017-04-01 and receivedDateTime lt 2017-05-01` | high       |
| `receivedDateTime` is a DateTimeOffset property serialized as ISO 8601 UTC       | S4     | "The date and time information uses ISO 8601 format and is always in UTC time. For example, midnight UTC on Jan 1, 2014 is `2014-01-01T00:00:00Z`."                        | high       |

Note: the official date-only example proves date-only works, but property-name casing is inconsistent in the example (`ReceivedDateTime` vs `receivedDateTime`) — treat casing as case-insensitive in practice but emit `receivedDateTime` for consistency. Timezone offsets (e.g. `-05:00`) are standard ISO 8601 for DateTimeOffset, but all official examples use `Z`; recommend normalizing inputs to UTC `Z` form server-side.

## Q6. Consistency requirement: $orderby + $filter

**Verdict: confirmed and important. When `$filter` and `$orderby` are combined on messages, orderby properties must appear in the filter, in the same order, before any other filter property — otherwise `InefficientFilter`.**

| Claim                                                         | Source | Quote / evidence                                                                                                                                                                                                                                                                                                                                                                                 | Confidence |
| ------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- |
| The three consistency rules and the `InefficientFilter` error | S3     | "1. Properties that appear in `$orderby` must also appear in `$filter`. 2. Properties that appear in `$orderby` are in the same order as in `$filter`. 3. Properties that are present in `$orderby` appear in `$filter` before any properties that aren't. Failing to do this results in ... Error code: `InefficientFilter` — The restriction or sort order is too complex for this operation." | high       |
| When `$filter` is specified, the service infers a sort order  | S2     | "When you specify `$filter`, the service infers a sort order for the results."                                                                                                                                                                                                                                                                                                                   | high       |
| Worked example of a compliant combination                     | S2     | `GET .../me/messages?$filter=Subject eq 'welcome' and importance eq 'normal'&$orderby=subject,importance,receivedDateTime desc`                                                                                                                                                                                                                                                                  | high       |

**Implication for the current handlers:** today `list-emails` always sends `$orderby=receivedDateTime desc` (`email/list.js:28`). Adding a `receivedDateTime` range keeps rule 1 satisfied (the orderby property appears in the filter), but the predicate ordering matters: with `$orderby=receivedDateTime desc`, `receivedDateTime` should appear **first** in `$filter`. A query like `$filter=isRead eq false and receivedDateTime ge X and receivedDateTime le Y` with `$orderby=receivedDateTime desc` risks `InefficientFilter` because `receivedDateTime` is not the first filter property. Safest emission order: `receivedDateTime ge X and receivedDateTime le Y and <other predicates>`, or drop `$orderby` when the filter is present (Graph infers sort order anyway). This must be encoded in the proposal's filter-builder contract.

## Synthesis (lane answers)

1. **Operators**: `ge`/`le`/`eq` (plus `lt`/`gt`/`ne`) are supported for DateTimeOffset. Literals are unquoted. Date-only literals (`ge 2017-04-01`) are officially valid for message date filters; full ISO 8601 UTC timestamps (`ge 2024-01-01T00:00:00Z`) are the canonical documented form. (S1, S4 — high)
2. **Endpoint support**: `$filter` on `receivedDateTime` is supported on both `/me/messages` and `/me/mailFolders/{id}/messages`; no documented restriction. The repo resolves both endpoints through `resolveFolderPath`, so the change composes with the existing folder layer. (S3, S1 — high)
3. **Combination**: predicates join with `and` without required parentheses. receivedDateTime composes with `isRead`, `hasAttachments`, and `from/emailAddress/address eq '...'` (navigation property). Predicate _ordering_ relative to `$orderby` is constrained by the InefficientFilter rules, not by parentheses. (S1, S3 — high, with one medium-inference cell)
4. **$search exclusion**: the repo's behavior (reject `$filter`/`$orderby` alongside `$search`on messages) is consistent with official docs, which document combination only for directory objects, never for messages, and never show`$filter` with `$search`on message examples. Doc-level explicit statement: UNVERIFIED; runtime verification cheap. KQL date *ranges* inside`$search`also UNVERIFIED (only single-date`received:` documented). (S5, S7)
5. **Paging**: the date predicate set in the initial request persists into every nextLink page (nextLink echoes all original query params). `$top` is 1–1000 (default 10). `count=0` full sweep is mechanically supported by `callGraphAPIPaginated(maxCount=0)`. `$search` responses cap at 1,000 items total. (S3, S5 — high)
6. **Ordering consistency**: InefficientFilter rules require the `$orderby` properties to appear first in the `$filter` expression, in the same order. The proposal's filter builder must emit `receivedDateTime` predicates first (or omit `$orderby` when a date filter is active). (S3, S2 — high)

## Implications for proposal

1. **Filter emission format**: `receivedDateTime ge <start> and receivedDateTime le <end>` — unquoted literals, UTC `Z` timestamps normalized server-side; accept date-only input and normalize to `T00:00:00Z`. Transport already URI-encodes `$filter` (`utils/graph-api.js:52-69`), so no new encoding work.
2. **Predicate ordering contract**: date predicates must be emitted before any additional predicates (isRead/hasAttachments/from) to satisfy the InefficientFilter rules given the existing `$orderby=receivedDateTime desc`; alternatively drop `$orderby` when a date filter is present.
3. **`list-emails`**: straightforward — add `receivedAfter`/`receivedBefore` (or equivalent) params merged into the existing `$filter` path; `count=0` full sweep already works via `callGraphAPIPaginated(maxCount=0)`. The hardcoded 50 cap (`email/list.js:27`) should be revisited in the same change (page size within 1–1000; sweep driven by `maxCount`, not page size).
4. **`search-emails`**: when search terms are present, date filters cannot ride on `$filter`. Two viable routes: (a) route date+terms queries to the boolean/`$filter`-only strategy (keyword search lost — acceptable if documented), or (b) translate dates to KQL (`received:<date>`); KQL ranges are unverified, so (a) is the evidence-backed default. When only boolean/date filters are present (no terms), existing `$filter` path applies unchanged.
5. **`$search` cap awareness**: even with date filters, keyword search results cap at 1,000 items — the "full sweep" guarantee only holds for the no-`$search` path.
6. **Testing**: `utils/mock-data.js` ignores query params, so `$filter` behavior is invisible in test mode; proposal must include extending the mock or using Graph mocks for handler-level date tests. `email/search.js` has no handler test file (`test/email/search.test.js` missing) — tests must be added in the same change.
7. **Spec surface**: greenfield for listing behavior; delta spec will be ADDED-only (`openspec/specs/email/spec.md` has no listing requirements today).
